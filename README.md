# 🎱 Система управления бильярдным клубом (Node.js)

Ядро системы: столы, тарифы, сеансы с посекундной тарификацией, живой
таймер на дашборде, история сеансов, журнал событий и абстракция
управления освещением (сейчас Mock, позже — реле MOES).

Стек: **Node.js 22.13+, Express, встроенный SQLite (node:sqlite)** —
никаких нативных зависимостей и компиляции при установке;
фронтенд — чистый HTML/CSS/JS без сборки.

---

## Установка

```bash
cd billiards-node
npm install
```

## Запуск

**Windows, без командной строки:**

- `start-club.bat` — двойной щелчок: поднимает сервер (свёрнутое окно)
  и открывает браузер; если сервер уже работает — просто открывает
  страницу. При первом запуске сам выполнит `npm install`.
- `autostart-install.bat` — запустить один раз: сервер будет
  стартовать автоматически (без окна) при каждом входе в Windows,
  останется только открыть http://127.0.0.1:8000 или закладку.
- `autostart-remove.bat` — отключить автозапуск.
- `create-developer.bat` — создать аккаунт разработчика (полный доступ)
  или вернуть доступ, если пароли забыты.

**Через терминал:**

```bash
npm run dev     # разработка: авто-перезапуск при изменении файлов
npm start       # обычный запуск
```

Откройте <http://127.0.0.1:8000> — страница входа.
Порт меняется переменной окружения `PORT`.

**Вход с телефона, планшета и ноутбука.** Сервер слушает все сетевые
интерфейсы сразу (`app.listen` без host), ограничений по адресам в
программе нет: подключаться можно по любому адресу компьютера. Все они
показаны в двух местах — в окне `start-club.bat` при запуске и в
программе: «Настройки» → «Доступ с телефона, планшета и ноутбука»
(там же ссылки и кнопка «Скопировать»). Список печатает
`src/print-network.js` тем же кодом, что и сервер (`services/network.js`).

Почему адресов несколько и почему работает не каждый:

- У компьютера обычно есть адрес на кабеле и адрес на Wi-Fi, а ещё
  адреса виртуальных адаптеров (VirtualBox, Hyper-V, WSL, VPN). Такие
  адаптеры помечены — с телефона они не откроются.
- Подходит адрес, у которого **первые три числа совпадают** с адресом
  устройства (`192.168.1.x` ↔ `192.168.1.x`). Телефон в мобильном
  интернете или ноутбук в гостевой Wi-Fi сети до клуба не достанут.
- Если не открывается ни один адрес — это брандмауэр Windows.
  `start-club.bat` заводит правило для порта 8000 **во всех сетевых
  профилях** (домашняя, рабочая, общественная), но для этого нужны права
  администратора: запустите файл правой кнопкой → «Запуск от имени
  администратора» (один раз). Без прав файл честно предупредит об этом,
  а не промолчит, как раньше.

### Обновление программы

Файлы распаковываются поверх старых, но **сервер обязательно нужно
перезапустить**: Node держит код в памяти, поэтому страница уже будет
новой, а сервер — старым. Именно это даёт загадочную пару симптомов:
`404` на запрос, которого старый сервер не знает, и `500` на том, что в
новых файлах уже исправлено. Порядок: закрыть окно «Сервер клуба» →
запустить `start-club.bat` → обновить страницу (Ctrl+F5).

Программа теперь сама это ловит: если файлы на диске новее запущенного
сервера, сверху появляется жёлтая плашка «Программа обновлена, но сервер
работает на старой версии». То же видно в «Настройки» → «Диагностика»
(строка «Код на диске»).

### Аккаунт разработчика и восстановление доступа

Готового встроенного логина в системе нет намеренно: аккаунт с известным
паролем — открытая дверь в кассу. Аккаунт разработчика создаётся на самом
компьютере клуба, одним запуском:

- **Windows:** двойной щелчок по **`create-developer.bat`**. Спросит логин
  (Enter — будет `dev`) и пароль (Enter — придумает сам, 12 знаков без
  похожих друг на друга символов), затем покажет логин и пароль. Сервер
  перезапускать не нужно — аккаунт работает сразу.
- **Через терминал:** `npm run add-user -- --role developer --login dev`
  (можно добавить `--password свой-пароль` и `--name "Имя"`).

Тем же способом создаётся любая роль (`--role owner|manager|admin|cashier`)
и возвращается доступ, когда пароли забыты: если логин уже есть, аккаунт
не дублируется — ему ставится новая роль, новый пароль и снова
разрешается вход. Это правомерно: у того, кто сидит за компьютером с
файлом базы, доступ и так полный, а операция пишется в журнал как
«Настройка на компьютере клуба».

Что даёт роль разработчика: полный доступ всегда, **в обход матрицы
«Роли и права»**. Это страховка — если в правах случайно снять все
галочки всем ролям, зайти и починить можно будет этим аккаунтом. Для
повседневной работы он не нужен: есть владелец, управляющий,
администратор и кассир.

### Инструменты разработчика

Всё это в «Настройках», в блоке **«Поддержка и обслуживание»**; часть —
только у роли «разработчик».

- **Пакет диагностики** — один текстовый файл: версия программы,
  состояние базы, версия схемы, сколько записей в каждой таблице,
  настройки клуба, сотрудники (без паролей), найденные нестыковки,
  последние запросы, журнал событий и весь `logs/errors.log`. Клиент
  присылает его вместо «у нас что-то не работает». Пароли, ключи Tuya и
  токен Telegram в файл не попадают.
  API: `GET /api/support/report`.
- **Доктор данных** — ищет расхождения, из-за которых отчёты врут:
  стол помечен занятым без сеанса (и наоборот), два открытых сеанса на
  одном столе, чек «активен» с нулевым остатком, сеанс со ссылкой на
  удалённого клиента, смена открыта больше суток и другие. Что можно
  починить безопасно — чинится кнопкой; то, что может стоить клубу
  денег, помечено «решает человек» и не трогается.
  API: `GET /api/support/checkup`, `POST /api/support/fix`.
- **Журнал запросов** — последние 200 обращений к программе: метод,
  адрес, код ответа, время и сотрудник. Отвечает на вопрос «что кассир
  нажал перед ошибкой». Живёт в памяти, в базу не пишется.
  API: `GET /api/support/requests`.
- **Перезапуск программы** кнопкой — нужен после обновления файлов.
  Работает, когда сервер запущен через `start-club.bat`: окно сервера
  держит `run-server.bat`, он и поднимает программу снова.
  API: `POST /api/system/restart`.
- **Демо-данные** (только разработчик) — «Наполнить демо-данными»
  добавляет показательные столы, клиентов и историю за 30 дней, чтобы
  было что показать в отчётах; «Стереть демо-данные» убирает ровно их.
  Все демо-записи помечены словом «Демо», рабочие данные не трогаются.
  API: `GET/POST/DELETE /api/demo`.
- **Запрос к базе только на чтение** (только разработчик) — один SELECT,
  не больше 200 строк. База открывается отдельным соединением в режиме
  «только чтение», поэтому изменить данные отсюда физически нельзя;
  каждый запрос пишется в журнал.
  API: `POST /api/support/query`, `GET /api/support/schema`.
- **Настройка клуба одним файлом** — переносит на другой компьютер
  только то, «как настроено»: настройки, тарифы и расписания, акции,
  расстановку зала, права ролей и меню. История, клиенты и сотрудники
  не переносятся; ключи Tuya и токен Telegram остаются на месте — они
  привязаны к компьютеру.
  API: `GET /api/config/export`, `POST /api/config/import`.
- **Версия схемы базы** — число в «Диагностике» и в пакете диагностики:
  сразу видно, с какой версии программы эта база и чего в ней ещё нет.

### Диагностика: где смотреть причину ошибки

«Внутренняя ошибка сервера» больше не безымянная:

- в ответе сервера приходит текст причины (браузер покажет её в
  уведомлении);
- все такие ошибки пишутся в файл **`logs/errors.log`** в папке
  программы — с временем, запросом и сотрудником;
- последние 20 ошибок и состояние базы видны в «Настройки» →
  «Диагностика»: версия программы, время запуска сервера, путь к базе,
  её размер, **проверка целостности** (`PRAGMA quick_check`), права на
  запись в папку и предупреждение, если папка лежит в облачной
  синхронизации (OneDrive и подобные — частая причина «database is
  locked»).

API: `GET /api/diagnostics` (право «Настройки»).

При первом запуске на пустой базе создаются стартовые данные:
3 стола, 2 тарифа и администратор — логин **admin**, пароль **admin**
(смените его после первого входа во вкладке «Сотрудники» → «Сбросить
пароль» или через `POST /api/auth/password`). Сидинг отключается
переменной `BILLIARDS_SEED=0`.

## Роли и кассовые смены

Вход обязателен для всех. Роли (что кому можно — настраивается в
«Настройки» → «Роли и права», доступно владельцу и разработчику):

- **Разработчик** — полный доступ всегда, в обход матрицы прав. Нужен,
  чтобы случайной правкой прав нельзя было закрыть вход всем сразу.
- **Владелец** — всё, включая редактор прав, бесплатное время и
  загрузку базы из копии.
- **Управляющий** — по умолчанию всё, кроме редактора прав и загрузки
  базы: столы, тарифы, сотрудники, настройки, отчёты, смены.
- **Администратор** — по умолчанию всё, кроме бесплатного времени,
  редактора прав и загрузки базы. Может работать со столами и без
  открытой смены.
- **Кассир** — залы (открыть/закрыть стол), история, журнал и своя
  кассовая смена. Остальные вкладки и API для него закрыты (403).

**Логин сохраняется как его ввели** — можно с заглавной буквы
(«Vladelec»), а входить разрешено в любом регистре: «vladelec» и
«VLADELEC» — тот же аккаунт. Занятым логин считается тоже без учёта
регистра. У полей пароля (вход, создание сотрудника, смена пароля) есть
**глазок** — пароль скрыт, но его можно показать и проверить.

Роли владельца, управляющего и разработчика назначает только владелец
или разработчик.

**Первая настройка клуба.** На свежей базе есть только администратор, а
владельца нет — и тогда получался замкнутый круг: роль «Владелец» в
списке спрятана (её выдаёт владелец), а «Роли и права» видны только
владельцу. Поэтому, **пока активного владельца/разработчика в системе
нет**, администратору (точнее — тому, у кого есть право «Сотрудники»)
открыты: роли «Владелец» и «Разработчик» в списке, раздел «Роли и права»
и загрузка базы из копии. Сверху при этом висит подсказка «Владелец
клуба ещё не создан». Как только владелец создан, всё это снова только у
него: администратор больше не выдаёт владельческие роли и не видит
редактор прав. Роль «Управляющий» в поблажку не входит — её выдаёт
только настоящий владелец.

Признак для интерфейса приходит с сервера в `/api/auth/me`:
`owner_level` (показывать владельческие блоки) и `owner_setup_pending`
(владельца ещё нет).

**Кассовая смена обязательна всем, кроме владельца и разработчика.**
Без открытой смены нельзя открыть стол, закрыть его и продлить чек —
иначе выручка повисает вне кассы и её не с кем сверить. Владельцу и
разработчику смена не нужна (они заходят посмотреть и настроить).

Кассовая смена: при входе кассира окно «Открытие смены» появляется
сразу (наличные в кассе на начало указываются в нём); управление
сменой — кнопка в шапке рядом с именем. При закрытии кассир вводит
фактические наличные — система считает расчётную сумму (остаток + наличная выручка)
и показывает расхождение (пересдача кассы). Выручка сеанса
привязывается к смене того, кто его закрыл. Кассир не может открыть или
закрыть стол без открытой смены. Все смены видны тем, у кого есть право
«Смены всех кассиров» (вкладка «Смены»), кассир — только свои
(`GET /api/shifts`).

## Касса: оплата, скидки, бар, чек

- **Закрытие стола** открывает окно с чеком: время (с учётом
  минимального оплачиваемого времени), скидка клиента, бар, итог с
  округлением по настройке клуба. Способ оплаты — наличные, карта или
  перевод — выбирается кнопкой, после чего печатается чек
  (окно печати). Из «Истории» тот же чек открывается **окном на странице,
  без печати** — посмотреть глазами; распечатать можно кнопкой в этом окне.
- **Клиенты** (вкладка «Клиенты») — база постоянных клиентов с
  телефоном и персональной скидкой (скидку назначает администратор,
  применяется только ко времени, не к бару). При открытии стола клиент
  выбирается в поле на карточке.
- **Бар отключён** — по просьбе клуба меню бара убрано из интерфейса
  (кнопка на столе, вкладка меню в настройках, отчёт по позициям).
  Данные и API (`/api/menu`, `/api/tables/{id}/orders`) сохранены, а
  право «Меню бара» спрятано из редактора прав — так бар можно вернуть,
  ничего не переписывая: снять `hidden` у права в
  `src/services/permissions.js` и вернуть блоки в интерфейс.
- **Сдача и доплата (оплата за время).** Если гость платил вперёд «за
  время», платят за фактическое время, даже если деньги уже в кассе.
  Взял час, поиграл 40 минут — при закрытии система посчитает 40 минут и
  покажет **сдачу** («Вернуть 200 ₸ и закрыть»); засиделся на 15 минут
  дольше — покажет **доплату**. В выручку идёт фактическая сумма, а не
  предоплата. Чтобы совсем короткие визиты не считались за копейки, есть
  настройка «Минимальное время сеанса».
- **Чек на остаток (фиксированная сумма).** По «Чеку на сумму…» деньги
  не возвращаем: гость заплатил 600 ₸, поиграл на 200 ₸ — при закрытии
  вместо сдачи выдаётся **чек на остаток 400 ₸** с коротким кодом вида
  `Ч-1234` (код показывается в окне и печатается на чеке). По этому чеку
  гость доиграет в любой другой день: правый клик по столу → «Открыть по
  чеку…», код можно ввести или выбрать из списка действующих чеков —
  система сразу показывает, на сколько времени хватит остатка.
  Перебор оплаченного времени доплачивается как обычно.
  Чек списывается целиком; если и по нему не догуляли — при закрытии
  выдаётся новый чек на новый остаток.
  Действующие чеки видны на вкладке «Клиенты» → «Чеки на остаток»,
  там же ошибочный чек можно отменить (право «Настройки»).
  **В деньгах это считается один раз:** выручка признаётся в момент
  оплаты (при открытии чека на сумму), а игра «по чеку» новой выручки не
  даёт и в кассовую смену не попадает — в отчёте по смене такие сеансы
  идут отдельно от нал/карта/перевод, и пересдача кассы сходится.
  API: `GET /api/vouchers`, `GET /api/vouchers/by-code/{код}`,
  `DELETE /api/vouchers/{id}`, открытие — `mode: "voucher"` с
  `voucher_code`.
- **Продление открытого чека** — правый клик по занятому столу →
  «Продлить время…»: добавить минуты или внести сумму, не закрывая стол
  (история сеанса сохраняется). Работает и когда оплаченное время уже
  вышло и стол мигает «ВРЕМЯ ВЫШЛО».
  API: `POST /api/tables/{id}/extend` с `minutes` или `amount`.
- **Клиент выбирается при открытии стола**: в окне «Открыть…» и «Чек на
  сумму…» есть поля тарифа и клиента; клиента можно набрать по имени или
  по телефону, его скидка сразу видна и попадает в расчёт.
- **Счёт клиента: деньги списываются сами.** Гость может внести деньги
  заранее (вкладка «Клиенты» → «Пополнить счёт»). Дальше платить второй
  раз не нужно: при открытии стола, продлении и закрытии сумма сначала
  списывается со счёта, а деньгами кассир добирает только разницу. Если
  счёта хватает на всё, выбирать наличные или карту не нужно — в окне
  появляется одна кнопка «Открыть со счёта». Галочку «Сначала списать со
  счёта клиента» можно снять, если гость хочет заплатить деньгами и
  сохранить счёт. Оплаченное вперёд, но не сыгранное время возвращается
  **обратно на счёт**, а не выдаётся из кассы — этих денег в ящике нет.
  Чеки на остаток и подарочные чеки сами не списываются: они у гостя на
  руках со своим кодом, и играют по ним через «Открыть по чеку…».
  **В деньгах это считается один раз:** пополнение — ещё не выручка,
  деньги просто легли в кассу движением «внесено»; выручкой они
  становятся в день игры. Поэтому оплата со счёта идёт в отчёте смены
  отдельной строкой «Со счетов клиентов», в наличные и карту не попадает,
  и пересдача кассы сходится.
  API: `POST /api/clients/{id}/topup`; открытие, продление и закрытие
  принимают `use_balance: false`, чтобы счёт не трогать.
- **Статистика клиента** — вкладка «Клиенты»: средний расход, всего
  времени и дата последнего визита в таблице, а по кнопке «Статистика» —
  свод за день, неделю, месяц и за всё время (визиты, расход, средний
  чек, время). API: `GET /api/clients/{id}/stats`.
- **Режимы открытия стола** — правый клик (или двойной клик) по столу:
  «Открыть…» с выбором «без ограничения времени» (оплата при закрытии)
  или «ограничение по времени» (клиент платит вперёд за 15 мин…2 ч,
  таймер идёт на убывание, по истечении стол мигает «ВРЕМЯ ВЫШЛО»), а
  также отдельные пункты «Чек на сумму…» (клиент платит фиксированную
  сумму — система считает оплаченное время по тарифу со скидкой; остаток
  вернётся чеком, а не деньгами) и «Открыть по чеку…» (игра на ранее
  выданный чек на остаток).
  Способ оплаты предоплаты запоминается и подставляется при закрытии.
- **Добавление и удаление столов — только в «Редакторе зала»**: на
  рабочей карте зала этих кнопок нет, чтобы кассир случайно не снёс стол.
  В палитре редактора есть форма «Столы» (название + тип), а удаляет стол
  инструмент «Ластик» кликом по столу (с подтверждением). Уйти из
  редактора с несохранёнными правками нельзя молча: при переходе на
  другую вкладку появится окно «Изменения не сохранены» с выбором
  «Сохранить и перейти» / «Уйти без сохранения» / «Остаться».
- **Вид «Карточки» убран** — зал показывается картой; карточка стола
  открывается двойным кликом по плитке.
- **Кнопка «Выбрать все»** появляется только после того, как выбран хотя
  бы один стол.
- **Редактор зала** (кнопка «⚙ Редактор зала» на карте, администратор):
  столы перетаскиваются по сетке и растягиваются за синий уголок
  (размер в клетках), стены и двери рисуются протяжкой мыши, ластик
  удаляет их; размер сетки настраивается. «Сохранить план» — расстановка
  хранится в базе и одинаково видна всем сотрудникам.
  API: `GET/PUT /api/plan`, `PUT /api/tables/{id}/layout`.
- **Брони** — тоже через правый клик по столу («Забронировать…»,
  «Отменить бронь»), с проверкой пересечений; на карточке стола
  показывается ближайшая бронь, за час до начала — оранжевым.
- **Тарифные расписания** (вкладка «Тарифы», администратор) — правила
  «дни недели + время → тариф»; система сама подставляет тариф при
  открытии стола (пометка «авто»), кассир может выбрать другой.
  Интервал «через полночь» (22:00–08:00) относится ко дню начала.
- **Настройки клуба** (вкладка «Настройки»): название клуба
  (показывается в шапке и на чеке), логотип клуба (в шапке рядом с
  названием и на странице входа), валюта, округление итога (нет / до
  рубля / до 10 ₽), минимальное оплачиваемое время сеанса, часовой пояс
  клуба (для расписаний и отчётов).
- **Логотип** загружается файлом (PNG, JPG, WebP, SVG, до 1 МБ), его
  **масштаб настраивается ползунком** («Настройки» → «Логотип клуба»:
  16–96 px по высоте, шапка меняется сразу) и хранится в самой базе — значит попадает в резервную копию и не
  теряется при переносе на другой компьютер.
- **Автоматическая копия базы**: раз в сутки программа сама кладёт копию
  в папку **backups** рядом с собой и хранит последние 14, удаляя старые.
  Видно в «Настройки» → «Диагностика», там же кнопка «Сделать копию
  сейчас». Раз в месяц копируйте эту папку на флешку — тогда данные
  переживут поломку компьютера.
- **База данных**: «Экспорт базы (.db)» сохраняет файл со всеми данными,
  «Загрузка базы из копии» заливает такой файл обратно, заменяя текущие
  данные (только владелец/разработчик). Копия из более старой версии
  программы тоже загрузится: переносятся те поля, что есть в обеих
  схемах, новые получают значения по умолчанию. После загрузки все
  входы сбрасываются — заходить нужно логином и паролем из копии.
- **Предупреждение о конце времени.** За 5 минут (настраивается) до
  конца оплаченного времени стол желтеет, вверху появляется полоска
  «Стол 3 — осталось 5 минут» и звучит короткий сигнал; когда время
  вышло — второе предупреждение. Время и звук: «Настройки» → «Клуб».
- **Пересадка гостей** — правый клик по занятому столу → «Пересадить на
  стол…»: сеанс, оплата, бар, клиент и таймер переезжают целиком,
  тариф остаётся прежним (цена не меняется).
  API: `POST /api/tables/{id}/move` с `target_table_id`.
- **Выдача и внесение денег в кассу** (кнопка «Касса» в шапке): выдали
  на закупку, сдали выручку старшему, внесли размен — с причиной и
  записью в журнал. Расчётные наличные меняются вместе с этим, поэтому
  пересдача сходится. Больше, чем есть в кассе, выдать нельзя.
  API: `POST /api/shifts/cash`, `GET /api/shifts/{id}/cash`.
- **X- и Z-отчёты.** X-отчёт («Смены» → «X-отчёт по моей смене» или
  кнопка в окне кассы) показывает, сколько должно быть в кассе прямо
  сейчас, и смену не закрывает. Z-отчёт печатается автоматически при
  закрытии смены — его сдают вместе с деньгами.
- **Акции «счастливый час»** (вкладка «Зоны и тарифы») — скидка на время
  игры по дням недели и часам, поверх любого тарифа. Со скидкой клиента
  **не складывается**: действует бо́льшая из двух. Скидка фиксируется при
  открытии стола и до конца сеанса не меняется. Кассир видит акцию прямо
  в окне открытия. API: `GET/POST/PUT/DELETE /api/promotions`,
  `GET /api/promotions/active`.
- **Подарок постоянным гостям** — «каждый N-й час в подарок»: когда
  выбранный клиент наиграет очередные N часов, при закрытии стола ему
  выдаётся **чек на бесплатный час** по цене текущего тарифа (обычный чек
  с кодом). Денег за подарок в кассу не приходило, поэтому в выручке он
  не считается. Настройка: «Зоны и тарифы» → «Подарок постоянным гостям».
- **Горячие клавиши** (подсказка по F1): «/» или F — быстрый поиск столов
  и клиентов (по имени и телефону), цифра 1…9 — выбрать стол по номеру,
  Enter — подтвердить в окне, Esc — закрыть окно или меню, С — смена.
  В полях ввода клавиши не перехватываются.
- **Уведомления** появляются справа наверху и складываются стопкой:
  об удачном действии коротко («Стол 1: сеанс открыт»), об ошибке —
  «Упс, что-то пошло не так» и причина под ним.
- **Печать чека под термопринтер**: «Настройки» → «Печать чека» — лента
  80 мм, 58 мм или обычный лист A4. Чек и отчёты смены верстаются точно
  по ширине ленты, без полей и переносов.
- **Работа с телефона**: на маленьком экране вместо карты зала —
  крупный список столов, меню уезжает вниз под большой палец, действия
  открываются кнопками во весь экран.
- **Зарплата** — «Отчёты» → «Зарплата»: часы работы (по кассовым сменам,
  открытая смена считается до текущей минуты), выручка его смен и
  начисление = часы × ставка + выручка × процент. Ставка и процент
  задаются в карточке сотрудника. API: `GET /api/payroll?days=N`.
- **Напоминания о бронях в Telegram** («Настройки»): за час (настраивается)
  до брони бот пишет **в чат клуба** — какой стол, во сколько, кто гость
  и телефон. Гостю бот написать не может: гость с ним не переписывался,
  поэтому звонит дежурный. Без токена и номера чата функция просто
  выключена. API: `POST /api/telegram/test`, `GET /api/telegram/status`.
- **Экран для гостей** — страница `/board` для телевизора в зале:
  свободные столы, цены и действующая акция крупным шрифтом, часы,
  обновляется сама. Вход не нужен, но выручки, кассы и имён клиентов на
  ней нет.
- **Отчёты**: кассовые смены с разбивкой нал/карта/перевод, выдачами и
  внесениями и пересдачей кассы; выручка по дням со способами оплаты;
  пиковые часы; нагруженность столов; зарплата сотрудников.

### Ограничения: по роли и лично

Два уровня, и личный сильнее:

1. **По роли** — «Настройки» → «Роли и права» (владелец/разработчик):
   восемь прав × четыре роли. Снятая галочка сразу убирает и вкладку в
   меню, и доступ к API — обойти через браузер нельзя.
2. **Лично на сотрудника** — «Пользователи» → «Изменить» → блок «Личные
   ограничения»: такая же таблица с галочками, как «Роли и права», и с
   таким же мгновенным сохранением. Колонка **«Доступ»** — что человек
   может на самом деле, колонка **«Откуда»** — откуда это право взялось:
   «по роли» или «лично разрешено/запрещено». Тронули галочку — решение
   стало личным (сильнее роли); кнопка **«↺ по роли»** возвращает как у
   роли. Так решается «этому кассиру скидки можно, а тому нельзя» без
   создания отдельной роли под каждого человека. В списке сотрудников у
   таких аккаунтов стоит отметка «личные ограничения».
   API: `GET/PUT /api/users/{id}/permissions`.

Что не даст сделать система: менять личные ограничения **себе** (иначе
можно закрыть себе доступ), урезать владельца, управляющего или
разработчика — это только владелец/разработчик, и ограничивать
**разработчика** (у него полный доступ всегда — редактор честно об этом
пишет). Личное решение живёт при смене роли и удаляется вместе с
аккаунтом.

Аккаунты сотрудников ведутся во вкладке «Сотрудники» (право
«Сотрудники»): создание (логин, имя, пароль, роль), кнопка «Изменить» —
карточка сотрудника с логином, именем, ролью, доступом и сменой пароля,
кнопки «Отключить»/«Включить» и «Удалить».

Ограничения, которые система не даст обойти: нельзя удалить или
отключить собственный аккаунт и сменить себе роль; нельзя оставить
систему без активного управленческого аккаунта (разработчик, владелец,
управляющий или администратор); логин должен быть уникальным. Если за
сотрудником есть история (смены, сеансы, заказы, брони), при удалении
аккаунт не стирается, а отключается — иначе порвались бы отчёты; в
журнале это видно как «Удалён сотрудник» с пояснением.

## Лендинг: страница о системе

На корневом адресе гостя встречает описание системы (`public/landing.html`):
для кого она, что умеет и чем полезна владельцу, администратору, кассиру
и владельцу сети. Сотрудник нажимает «Войти» и попадает на форму входа;
войдя один раз, дальше видит сразу рабочий стол — сессия живёт месяц.

Страница доступна и по прямой ссылке `/about` — она работает всегда,
независимо от настройки ниже.

**Клубу, которому витрина на рабочем месте не нужна,** достаточно
поставить переменную окружения `WESPRO_LANDING_ROOT=0`: тогда корень
снова сразу ведёт на вход, как раньше.

Вёрстка своя (`public/landing.css`), но на тех же переменных темы и
иконках, что и рабочий интерфейс, поэтому светлая и тёмная тема
работают одинаково. Контакты в блоке призыва — заглушки: их нужно
вписать в `landing.html` перед тем, как показывать страницу клиентам.

## Кабинет клуба: регистрация и вход по почте

С лендинга можно зарегистрировать клуб самостоятельно — без участия
владельца сервиса. Кнопка «Регистрация» ведёт на `/account/register`:
название клуба, имя и фамилия владельца, почта, пароль. Пробный период
начинается сразу же, тем же способом, что и при ручном добавлении клуба
в панели сети (`/hub`) — разницы для подписки нет.

Дальше вход — **по почте и паролю**, на `/account/login`. Это третий,
отдельный вид входа в систему, не пересекающийся с двумя другими:

| Вход | Кто | Чем входит | Что видит |
|---|---|---|---|
| `/login` | сотрудник клуба на месте | логин + пароль | свой клуб: касса, столы, отчёты |
| `/hub/login` | сотрудник WesPro | логин + пароль | всю сеть клубов |
| `/account/login` | владелец клуба (клиент сервиса) | **почта + пароль** | только карточку своего клуба |

У кабинета своя cookie (`wespro_club_session`, `Path=/account`) и свой
роутер (`src/hub/account-routes.js`), поэтому эти три входа физически не
могут перепутаться: сессия одного не открывает другой, даже случайно.
Данные при этом общие — кабинет читает ту же базу хаба (`hub.db`), что и
панель `/hub`; клуб, заведённый в панели вручную, просто не может войти
по почте, пока владелец сервиса (или сам клуб повторной регистрацией той
же почтой) не задаст пароль.

В кабинете видно: статус подписки, тариф, до какого числа оплачено,
историю оплат (только своих — чужие клубы не видны) и ключ доступа для
программы клуба. Пароль меняется тут же, по старому паролю.

Оттуда же — кнопка **«Открыть программу»** и ссылка для сотрудников; про
них следующий раздел.

**Чего в кабинете пока нет** — оплаты онлайн (отмечает оплату только
владелец сервиса в панели `/hub`) и подтверждения почты письмом (SMTP в
проекте не настроен).

## Облачная версия: много клубов на одном сервере

Переменная `WESPRO_NETWORK=1` включает сетевой режим: один сервер
обслуживает всю сеть клубов сразу (так работает wespro.uz). Без неё
ничего не меняется — обычная установка на один клуб, как и была.

На Railway её ставят в Variables у сервиса; путь к базам клубов уже
прописан в `Dockerfile` (`WESPRO_CLUBS_DIR=/data/clubs`) — это тот же
подключённый диск, что и у остальных баз. Без диска, смонтированного в
`/data`, базы клубов пропадут при первом же обновлении.

Пока режим выключен, кабинет не показывает кнопку «Открыть программу» и
ссылку для сотрудников: программа в такой установке стоит на компьютере
клуба, а не на этом сервере, и вести им было бы некуда.

**У каждого клуба своя база** — файл `data/clubs/<id>/billiards.db` и
свой экземпляр приложения. Разделение по файлам выбрано намеренно, вместо
колонки `club_id` в общих таблицах: обрабатывая запрос одного клуба,
программа физически не имеет подключения к базе другого. При общих
таблицах достаточно один раз забыть `AND club_id = ?` в одном запросе из
сотни, чтобы кассир одного клуба увидел выручку соседнего.

Приятное следствие: вся деловая логика (`src/services/*`) и все маршруты
(`src/routes/api.js`) остались нетронутыми — они и раньше принимали базу
параметром. Мультиарендность добавлена снаружи: `src/tenants.js` (реестр
баз клубов) и `src/network-app.js` (кому отдать запрос).

**Как браузер сообщает, в какой клуб идёт запрос.** В cookie
`wespro_club` лежит короткий адрес клуба в сети. Он попадает туда одним
из трёх способов:

* владелец нажал в кабинете «Открыть программу» — и сразу оказывается в
  программе: он уже доказал, кто он;
* сотрудник открыл читаемую ссылку клуба вида
  `/login/adminpanel/<название-клуба>` (её показывает кабинет), либо
  ввёл код клуба на странице входа («Сотрудник клуба? Войти по коду
  клуба») — тот же смысл, только код короче диктовать по телефону, а
  ссылку на новом устройстве иначе не взять;
* владелец ввёл на входе почту, которой регистрировал клуб.

Сама по себе cookie никуда не пускает: она только выбирает клуб, а
дальше работает обычный вход по логину и паролю.

База клуба заводится лениво — при первом обращении, а не при регистрации:
брошенные на полпути регистрации не оставляют пустых баз. При заведении
создаётся владелец (логин — его почта, пароль тот же, что и в кабинете),
стартовые столы и тарифы, название клуба и ключ доступа в «Настройках».
Учётки `admin/admin` в сети не создаётся: сюда ведёт публичный адрес.

Что закрыто в облачной версии:

* **перезапуск сервера, адреса машины и общий журнал внутренних ошибок**
  (`/api/system/restart`, `/api/network`, `/api/diagnostics`,
  `/api/support/report`) — сервер общий, это дело поддержки WesPro;
* **программа заблокированного клуба** — вместо неё страница «подписка
  приостановлена». Личный кабинет при этом открыт, иначе оплатить было
  бы негде.

Состояние, которое живёт в памяти процесса, тоже разделено по базам:
журнал запросов (`src/services/request-log.js`) и драйвер освещения
(`src/services/lighting.js`). Иначе администратор одного клуба видел бы
запросы другого, а команда «включить свет» уходила бы в чужой аккаунт.

**Чего в сетевом режиме пока нет:** автоматических копий баз и
напоминаний в Telegram по каждому клубу — и то, и другое сейчас
рассчитано на одну базу на процесс (см. пункт про офлайн-синхронизацию).

## Сеть клубов: центральная панель

Одна программа — один клуб. Когда клубов становится много и каждый из
них платит за подписку, нужна отдельная панель поверх них: кто заплатил,
кто просрочил, кто вообще пропал со связи. Она живёт по адресу `/hub`
и к работе самого клуба отношения не имеет.

**Это два разных рабочих места.** У панели своя база (`hub.db`), свой
вход и своя cookie: сотрудник клуба не попадает в панель даже с
действующей сессией клуба, а владелец сервиса своей сессией не попадает
в кассу клуба. Данные о подписках не потеряются, если базу клуба
восстановят из копии, — они лежат отдельно.

Первый вход: при первом запуске панель заводит владельца сервиса и
печатает логин с паролем в окне сервера. Пароль можно задать заранее
переменными `WESPRO_HUB_LOGIN` и `WESPRO_HUB_PASSWORD` — на хостинге так
и нужно, иначе он окажется в логах.

`WESPRO_HUB_PASSWORD` работает и как запасной ключ от этой двери: если
она задана, пароль ставится и уже заведённому владельцу. Иначе панель со
всеми клубами закрывалась бы навсегда — сгенерированный пароль печатается
единственный раз, а на хостинге логи того запуска давно уехали. Пока
переменная задана, пароль ставится заново при каждом запуске, поэтому
после входа его меняют в самой панели, а переменную убирают — сервер об
этом прямо предупреждает в логе.

Что есть в панели:

- **Сводка** — сколько клубов в сети, кто платит, кто на пробном
  периоде, сколько денег в месяц приносит сеть, и список «требует
  внимания»: у кого заканчивается подписка, кто просрочил, кто давно не
  выходил на связь, кто только что зарегистрировался. Клик по строке
  открывает карточку клуба.
- **Клубы** — название, город, контакты, тариф, статус подписки и когда
  клуб последний раз был на связи. Зелёная точка у названия — программа
  клуба отмечается; серая — молчит.
- **Подписка и оплата** — отметка оплаты вручную с историей платежей:
  сумма, срок, чем платили, кто провёл. Оплата вперёд не съедает уже
  оплаченные дни (продлеваем от текущей даты, а не от сегодня), а
  просроченному клубу считаем от сегодня — за простой никто не платит.
- **Автоблокировка при просрочке.** Статус считается из дат, а не
  хранится «на честном слове»: пока оплата действует — «активна», после
  неё несколько дней «просрочена» (клуб работает, но попал в список
  «позвонить»), потом «заблокирован». Сроки настраиваются. Отсрочка
  («оплатят на следующей неделе») держит клуб включённым, а оплата
  снимает и отсрочку, и ручную блокировку. Ручная блокировка сильнее
  любых дат.
- **Тарифы сервиса** — свои планы: цена, период, лимит столов, что
  входит. Тариф, на котором сидят клубы, не удаляется — его можно только
  отключить, иначе клуб остался бы без плана.
- **Сообщения клубам** — одному клубу или всем сразу. Сообщение не
  «отправляется» по сети, а ждёт в панели: выключенный сейчас клуб
  получит его при первом же включении. Видно, сколько клубов прочитали.
- **Вход «от лица клуба»** — одноразовый ключ на 30 минут с обязательной
  причиной. Ключ сгорает после первого входа, а причина попадает в
  журнал сети — постоянного доступа в чужой клуб нет ни у кого.
- **Журнал сети** — регистрации, оплаты, смены статуса, блокировки,
  входы поддержки, выдача ключей.

**Как клуб связывается с панелью.** В карточке клуба выдаётся ключ
доступа — его вписывают в программу клуба один раз. Дальше программа
сама отмечается на связи:

```
POST /hub/api/agent/ping
X-Club-Key: <ключ клуба>
{ "version": "1.1.0", "tables": 8 }
```

В ответе — статус подписки, до какой даты оплачено, лимит столов и
непрочитанные сообщения. Автоблокировка работает именно так: панель
ничего никуда не «пушит», клуб сам узнаёт из ответа, оплачен он или нет.
Ключом клуба нельзя посмотреть ни соседей, ни чужие оплаты — только своё.
Если ключ утёк вместе с компьютером клуба, в карточке выдаётся новый:
старый перестаёт работать сразу.

## Работа с БД

- СУБД — SQLite (встроенный модуль node:sqlite), файл `billiards.db` в корне проекта
  (создаётся автоматически при старте, в git не попадает).
- Путь можно переопределить: `BILLIARDS_DATABASE_PATH=C:\data\club.db`.
- Таблицы создаются автоматически (`CREATE TABLE IF NOT EXISTS`).
- Внешние ключи включены (`PRAGMA foreign_keys = ON`), режим WAL.
- Время хранится в UTC (ISO-8601 с суффиксом `Z`), браузер показывает
  локальное время.
- Деньги: цена тарифа — целые рубли в час; итоговая стоимость хранится
  **в копейках целым числом** (никаких float в БД), наружу отдаётся в рублях.
- Начать с чистой базы: остановить сервер и удалить `billiards.db`.

уже идущие сеансы. Живой таймер устроен так: сервер отдаёт
`elapsed_seconds` и `current_cost`, фронтенд лишь тикает между
опросами — поэтому обновление страницы ничего не сбрасывает.

## Как добавить стол

Через интерфейс: вкладка «Залы» → поле «Название нового стола» →
**Добавить стол**.

Через API:

```bash
curl -X POST http://127.0.0.1:8000/api/tables \
  -H "Content-Type: application/json" \
  -d '{"name": "Стол 4"}'
```

Названия столов уникальны; дубликат вернёт `409`.

## Как добавить тариф

Через интерфейс: вкладка «Тарифы» → название и цена → **Добавить тариф**.

Через API:

```bash
curl -X POST http://127.0.0.1:8000/api/tariffs \
  -H "Content-Type: application/json" \
  -d '{"name": "Ночной", "price_per_hour": 300}'
```

Цена — целое число рублей в час, больше нуля. Названия уникальны.

## Освещение: какие реле подходят

Свет над столом включается при открытии сеанса и гаснет при закрытии.
Тип устройства выбирается **для каждого стола отдельно** («Настройки» →
«Привязка столов к реле»), поэтому в одном клубе можно держать разные
реле — что нашлось в магазине, то и подключили.

Настройка реле — **только у роли «разработчик»**: ни владелец, ни
администратор, ни управляющий этих разделов не видят и не могут дёрнуть
их API напрямую (учётные данные Tuya и адреса устройств — не то, чем
должен управлять кассир или даже владелец клуба). Обычное управление
светом — включить/выключить вручную, автоматика при открытии/закрытии
стола — остаётся доступно всем, у кого есть право «Столы».

| Тип | Что это | Что нужно |
|---|---|---|
| **Tuya / MOES** | WM4LT1 и любые Wi-Fi реле экосистемы Tuya (MOES, Avatto, Aubess, Girier, Lonsonho…) | интернет, аккаунт Tuya IoT, ключи в настройках; устройство выбирается из списка |
| **Tasmota** | Sonoff Basic/4CH, Blitzwolf и любые реле с прошивкой Tasmota | только адрес в локальной сети, например `192.168.1.50`. Интернет не нужен |
| **Shelly** | Shelly 1/1PM (Gen1), Shelly Plus/Pro (Gen2) | адрес в локальной сети. Поколение программа определяет сама |
| **Своё устройство** | ESPHome, Home Assistant, самодельные реле на ESP — всё, что умеет HTTP | два адреса: «включить» и «выключить» |

Локальные реле (Tasmota, Shelly, своё устройство) **надёжнее облачных**:
они работают без интернета и отвечают за миллисекунды, а не через
сервер в другой стране. Если интернет в клубе пропадёт, столы на Tuya
останутся без света, а локальные продолжат работать.

Кнопка **«Тест»** в таблице привязки щёлкает реле на 2 секунды — так
проверяют, тот ли это стол. Свет можно включить и вручную: правый клик
по столу → «Включить свет» (доступно всем с правом «Столы»). Кнопка
**«Привести свет в порядок»** (только разработчик) включает лампы над
занятыми столами и гасит над свободными — это же делается само при
запуске программы.

Адреса устройств: Tasmota показывает свой IP в веб-интерфейсе реле,
Shelly — в приложении; ещё их видно в списке устройств роутера. Чтобы
адрес не менялся, закрепите его в роутере за этим устройством
(«DHCP reservation» / «Статический IP»).

## Устройства зала: кондиционер, вытяжка, приток

Это не столы: у них нет сеансов, тарифов и времени. Устройство сидит на
реле — любом из таблицы выше, тем же способом, что и свет над столом, —
и работает **по циклу**: поработало столько-то минут, постояло
столько-то, и так по кругу. Типичная вытяжка: 15 минут работает, 30
стоит.

- Свой раздел в меню — **«Устройства»**. Наверху — плашка на каждое
  устройство: работает или стоит, через сколько переключится, кнопки
  **«Включить/Выключить»** и **«Цикл N/M»**. Их видят все сотрудники —
  это как выключатель на стене.
- На экране «Залы» устройства не мешают столам: под легендой — полоска
  из иконок, по одной на устройство. Цвет — состояние: зелёная —
  работает, серая — стоит, красная — реле не отвечает; у решётки рядом
  процент. Навести — подробности, клик — те же кнопки управления.
- Рядом с названием на плашке — связь с реле: **в сети** (ответило на
  последний опрос), **нет связи** (молчит — питание, Wi-Fi), «без реле»
  или «не проверяется» («своё устройство» опросить нечем). Реле
  опрашиваются раз в полминуты; кнопка «Проверить связь сейчас» — не
  дожидаясь. Тут же таблица **«Реле: столы и устройства»** — все реле
  клуба: тип (над каким столом или у какого устройства — мелко
  рядом), **IP и MAC**, связь, состояние (свет над столом переключается
  отсюда же, право «Столы») и когда реле последний раз выходило на
  связь. IP и MAC реле сообщает само при опросе: Tasmota — оба
  (`Status 5`), Shelly — MAC (`/shelly`), Tuya — только IP из облака;
  что не сообщило — вписывают руками прямо в таблице (столы —
  разработчик, устройства — право «Настройки»). У реле в локальной сети
  IP — это адрес привязки: сменился адрес — поправили здесь, и реле
  снова отвечает. Время последней связи держится в памяти программы:
  после перезапуска отсчёт заново. `GET /api/relays`,
  `POST /api/relays/probe`, `PUT /api/relays/table|device/:id/net
  { "ip": "192.168.1.50", "mac": "A4:CF:12:34:56:78" }`.
- Настройка устройств (название, вид, цикл или положения, реле) — в
  «Настройках», в блоке разработчика, рядом с привязкой столов к реле:
  адреса и ключи реле — не то, чем управляет кассир. Кнопка «Тест»
  щёлкает реле на 2 секунды.
- **Виды.** Кондиционер, вытяжка и приток — выключатель с циклом.
  **Решётка канала** — положения в процентах, например `30,50,70`:
  на плашке кнопка на каждое положение и «Закрыть». Решётка с одним
  положением (например `100`) — заслонка «открыто/закрыто» на обычном
  реле (те же Tuya-выключатель, Tasmota, Shelly). С несколькими —
  привод: Tuya — команда `percent_control`, Tasmota с прошивкой под
  шторы — `ShutterPosition`, Shelly в режиме roller/cover, «своё
  устройство» — адрес включения с подстановкой `{percent}`
  (`http://192.168.1.60/set?pos={percent}`). Цикла у решётки нет;
  «включить» для неё — открыть до упора.
- **На плане зала.** В «Редакторе зала» в палитре есть раздел
  «Устройства»: выберите устройство и кликните на план — так их
  расставляют по комнатам. Уже стоящие в списке не показываются
  (одно устройство — одно место); ластик снимает с плана, само
  устройство остаётся. На карте зала плитка устройства показывает,
  работает ли оно (зелёная рамка) и положение решётки; клик по ней
  открывает те же кнопки, что на вкладке «Устройства». Удалили
  устройство — исчезло и с плана.
- Цикл начинается с работы. Ручное «включить» во время цикла начинает
  его заново: полные N минут работы, потом пауза; «выключить» — полную
  паузу, потом работа. Выключение цикла выключает и само устройство:
  ничего не должно крутиться без присмотра. Хотите, чтобы работало
  постоянно, — выключите цикл и нажмите «Включить».
- Фаза считается от момента запуска цикла, а не «накапливается»:
  перезапуск программы, пропущенный тик и молчащее реле цикл не сбивают —
  каждые 30 секунд программа приводит реле к тому, что должно быть
  сейчас. Реле, которое не отвечает, видно прямо на плашке; в
  `logs/errors.log` оно попадает один раз, а не каждые полминуты.
- В облачной версии (`wespro.uz`) до реле в локальной сети клуба сервер
  не дотянется — там работают только облачные Tuya/MOES. Локальные
  Tasmota и Shelly — для установки на компьютер клуба.
- «Настройка клуба одним файлом» переносит устройства (название и
  цикл), но не реле — его подключают на месте, как и свет над столами.

API: `GET /api/devices`, `POST /api/devices`, `PUT /api/devices/:id`,
`DELETE /api/devices/:id` (право «Настройки»), `POST /api/devices/:id/power
{ "on": true }`, `POST /api/devices/:id/cycle { "on": true }`,
`POST /api/devices/:id/position { "percent": 50 }` (любой сотрудник).
Устройство на плане — элемент плана `{ "type": "device", "device_id": 3, … }`. Ручные переключения и запуск/остановка цикла пишутся в
журнал; автоматические — нет, это шум.

## Освещение: реле MOES WM4LT1 (Tuya)

Свет включается при открытии сеанса и гаснет при закрытии; оба события
пишутся в журнал. Доступны два драйвера (`src/services/lighting.js`):

- **mock** (по умолчанию) — состояние в памяти, оборудование не нужно;
- **tuya** — реальные Wi-Fi реле экосистемы Tuya (MOES WM4LT1 и
  совместимые) через официальный Tuya Cloud API
  (`src/services/lighting-tuya.js`). На открытие сеанса устройству
  уходит команда `switch=true`, на закрытие — `switch=false`.

Команды отправляются асинхронно: если облако недоступно, сеансы
открываются и закрываются как обычно, а ошибка попадает в лог сервера.
Стол без привязанного устройства тоже работает — команда просто
пропускается с предупреждением.

Вся настройка выполняется **во вкладке «Настройки» интерфейса** — код и
файлы править не нужно. Настройки и привязки хранятся в базе.

### Как подключить реле — по шагам

1. **Подключите модуль к Wi-Fi** через приложение Smart Life (или Tuya
   Smart) как обычно — реле должно включаться из приложения.
2. **Создайте облачный проект** на <https://iot.tuya.com>:
   Cloud → Create Cloud Project. Data Center выберите тот же, что у
   аккаунта приложения (для России/Европы — Central Europe).
   В проекте подключите API «IoT Core» (Service API → Go to Authorize).
3. **Привяжите аккаунт приложения**: в проекте Devices → Link App
   Account → отсканируйте QR-код приложением Smart Life — реле появятся
   в списке устройств проекта.
4. **Возьмите ключи проекта**: вкладка Overview → Access ID и
   Access Secret.
5. **В интерфейсе клуба** откройте вкладку «Настройки»:
   - драйвер — «Tuya / MOES», дата-центр — ваш, впишите Access ID и
     Access Secret → «Сохранить подключение» (появится
     «✅ Подключено к Tuya»);
   - нажмите «Загрузить устройства из Tuya» и в таблице ниже выберите
     для каждого стола его реле и канал (для многоканального модуля —
     Канал 1…4); привязка сохраняется сразу при выборе;
   - кнопка «Тест» щёлкает реле на 2 секунды — удобно проверить, что
     выбран правильный модуль.
6. Готово: при нажатии ОТКРЫТЬ на столе реле включится, при ЗАКРЫТЬ —
   выключится.

Соответствующие API (их использует вкладка «Настройки»):
`GET/PUT /api/settings`, `GET /api/settings/devices`,
`PUT /api/tables/{id}/device`, `POST /api/tables/{id}/light`.

Переменные окружения (`BILLIARDS_LIGHTING`, `TUYA_ACCESS_ID`,
`TUYA_ACCESS_SECRET`, `TUYA_API_HOST`) остаются как значения по
умолчанию, пока настройки не сохранены через интерфейс.
